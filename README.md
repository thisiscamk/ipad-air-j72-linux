# iPad Air 1 Cellular (J72) Linux bring-up

An experimental, tethered **RAM-only** Linux and Omarchy A desktop project for the iPad Air 1 Cellular (`iPad4,2` / `J72AP`). The iPad's iOS installation and internal storage remain intact.

Read the [progress report](J72-PROGRESS.md) for measured results and current limits, the [process guide](PROCESS.md) for the checks and RAM boot sequence, the [roadmap](ROADMAP.md) for milestones, the [DFU session plan](DFU-PLAN.md) for proposed test batches, the [Pi charging plan](PI-CHARGING-PLAN.md) for keeping USB data attached while charging, and the [internal-storage plan](INTERNAL-STORAGE-PLAN.md) for the later installation gates.

The present desktop uses software rendering and a read-only Arch Linux ARM filesystem served by a Raspberry Pi over USB. Native multitouch now reaches Linux input, and the owner has confirmed full-screen touch mapping with a visual target test. This repository is a place to share reviewed notes while J72 support is developed; a focused hardware implementation may later be proposed to [OrchardLinux/orchard](https://github.com/OrchardLinux/orchard).

**Touch milestone:** correcting an omitted shared analog-power enable changed the result from zero-contact reports to real native touch: 542 one-finger and 50 two-finger reports during the owner's gestures, with nine matched press/release lifecycles and no contacts left down. The capture passed firmware health and hardware restoration checks. A Linux multitouch device now drives a visual target/trace test; the owner confirmed accurate mapping across the screen. The owner has also opened desktop menus and launched Foot by touch. On-screen keyboard typing and its bar toggle also work. The latest cold RAM boot automatically started touch and the desktop; window dragging and tap-to-keyboard behavior now work in the live session.

Private firmware, device calibration, identifying logs, and local disk images are intentionally excluded.

**Latest charging milestone:** the powered-hub 850 mA / 30-second trial retained live USB data and reached **−10…+37 mA** battery current, from −773 mA baseline. Rollback passed; sustained charging remains unqualified. The iPad is back in iOS and reports charging on the same hub. See the [current result](PI-CHARGING-PLAN.md#31-october-powered-hub-trial-completed-back-in-ios).

**Working source:** [code/](code/) now contains the measured SPI driver, touch worker and decoder, HDQ battery frontend, bounded charging diagnostics, desktop changes and offline tests. Private firmware/calibration are supplied separately. [Native Orchard integration work](code/UPSTREAM-PLAN.md) remains before resubmission.

**Interim upstream contribution:** [draft Orchard PR #43](https://github.com/OrchardLinux/orchard/pull/43) now includes the working SPI, touch, battery and tested 425 mA development sources under `experiments/j72/`, plus the J72 report. Review remains on hold pending native Orchard integration and exact-revision hardware qualification.

**Earlier capacity session:** the revised kernel booted and corrected the exported remaining/full capacity pairing. The two values agreed with 100% charge at startup; later readings also followed the reported percentage. Automatic touch and desktop startup passed again. The touch worker stopped after 2,619 emitted frames with no rejected layouts, SPI errors, timeouts or recoveries, and passed firmware health and hardware cleanup. The previous cold boot already passed the owner's repeated keyboard hide/tap/type check.

**Earlier USB recovery issue:** the earlier wall-charger recording was lost when USB failed on return to the Pi and the owner subsequently reported a Pi hang. The revised image now displays live battery readings on screen, confirmed by the owner. Two Home-button USB rebinds enumerated without new host USB errors. Network access recovered, but serial access failed after the first rebind and network access subsequently stopped too. A second rebind restored sustained network access without opening serial. This is partial recovery, with the cause unresolved. **That earlier session showed no Linux wall charging**; the wall observation below shows net discharge. The Pi kernel and original desktop image are unchanged, and battery-health estimates remain unqualified.

**Next priority after battery reporting:** bring up and measure Linux charging before Wi-Fi work. The [B04C charging plan](DFU-PLAN.md#immediately-after-battery-reporting-b04c-charging-bring-up) uses a RAM-only recorder for wall-charger tests; the USB-backed desktop will be detached before cable changes. Brief net charging now passes the bounded test below; sustained charging remains unqualified.

**Wall-charger result:** the owner confirmed both supplied photos were taken on the wall charger. They show 88% → 86%, 4.046 → 4.037 V and −743 / −746 mA over 161 seconds: **net discharge in this Linux session**. The cause remains unresolved; no charger controls were changed. The desktop/input/export had been stopped and Home recovery disabled. The owner has since confirmed iOS is visible and charging on the wall charger.

**Earlier charger finding:** owner-confirmed wall-charger photos show the same input-limit code as the Pi baseline: `0x04c0 = 0x02`, about 100 mA nominal. Input suspend remains clear, and the battery-current setting and ceilings are nonzero. Battery current stays near −743 mA, with charge falling 89% → 87% across the two photos. All 18 observed PMIC values are unchanged. This points to input-current policy/source detection for the next test; it does not yet prove the cause or measure actual USB input current. No charger settings were changed. The owner has confirmed iOS is visible and charging. The source is a powerboard USB socket whose rating remains unconfirmed. This motivated the single 425 mA / 30-second comparison reported below. No higher-current step was enabled.

**Controlled charging result:** the one-shot 425 mA input-limit test ran on the wall charger. Battery current changed from −764 mA before the test to −423…−400 mA across 12 retained trial samples, then returned to −767 mA after automatic restoration of the original 100 mA input setting. Active-phase readback and the final restored state were photographed; no restoration error was reported. This reduced net discharge by about 45–48%, supporting a substantial contribution from the inherited input limit. **The battery still did not charge.** The owner has returned to iOS and confirmed charging. The owner has now supplied a separate charger and confirmed its 5 V / 1 A label. The later fixed 850 mA / 30-second comparison on that separate source has now produced +20…+51 mA across 12 samples, compared with −766 mA before and −765 mA after verified automatic restoration. The owner confirms iOS recovery and charging. This proves brief net charging; sustained charging and source/protection policy remain open.
